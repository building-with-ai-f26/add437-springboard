Living PRD (Product Requirements Document)

Updated every week as we test with real users and learn what works.

1. Target User & The Job to Be Done

Who is this for? Beginner and intermediate DJs who want to build sets from playlists and don’t yet have harmonic mixing memorized.

The painful "Before" workflow: I would curate a playlist of songs, but I would pick the next track by gut feel or by checking BPM and key on a lookup site one song at a time. I don’t really know which key jumps are safe, so transitions sometimes clash, and I can’t plan where the energy goes. This was also a very manual process that was not sustainable for longer sets.

The "After" workflow with this product: I pick the song that’s playing, and the tool ranks the best next tracks from my list. For each one it says what kind of move it is (smooth, energy boost, mood shift) and why, so I learn Camelot mixing while I plan.

2. Scope & Explicit Non-Goals

  • In Scope (Core Workflow): Load or enter a list of songs with BPM and Camelot key → pick the current song → see the next-song options ranked by compatibility, each with a plain-English explanation → add one to the queue and repeat.
  • Out of Scope #1: It doesn’t play or mix audio.
  • Out of Scope #2: It doesn’t control Spotify or its DJ feature.
  • Out of Scope #3: It doesn’t detect BPM or key from audio files; songs are entered manually for now.

3. How It Works Under the Hood & Riskiest Assumption (Week 2+)

Riskiest Assumption: Spotify no longer gives new apps BPM or key data, so the app needs another way to fill a DJ’s crate. The risk is that an AI model can’t suggest real songs with BPM and Camelot keys accurate enough to mix. If its suggestions are wrong, the set it builds will clash.

How Build 2 tests it: The “Suggest songs that fit” button in My crate asks an AI model (via OpenRouter) for real songs in the keys and tempo range the set needs. I check its suggestions against Spotify’s Mix view, which shows each track’s BPM and key, and note how many are right.

Simple Architecture (v3): Browser (the app at /app/, sets saved in the browser) → my Python server on Render (rate limits, size checks, keeps the API key secret) → OpenRouter AI model, with web search to verify BPM, key and genre → JSON back to the app.

Hosting, data & security (PRD v3): Hosted on Render’s free tier at https://dj-app-6xjr.onrender.com. No database and no sign-in: each visitor’s sets live in their own browser, so there’s no shared data to protect. The OpenRouter key is stored only in Render’s environment settings. The AI route allows 20 requests per visitor per 10 minutes and 300 per day overall, and my OpenRouter key has a hard spending cap. Full audit in SECURITY.md.

Build 1 · Intent.md & Throwaway Prototype (Due Nov 9)

  • What shipped: A single-page prototype (screenshot above). You pick the song that’s playing and it ranks every other song by Camelot key compatibility (smooth, mood shift, energy boost, or clash) and BPM gap (±6% = easy blend), with a one-sentence explanation for each. You can paste in your own songs as “Title - Artist, BPM, Key” and build a queue.
  • Things learned with AI: How to direct a coding agent (Claude Code) with a specific prompt, how branches and pull requests work, and how GitHub Pages publishes the docs folder. Spotify’s API no longer gives new apps BPM or key data, so I had to design around entering songs manually.
  • What broke / changed in PRD: My original idea was a Spotify DJ extension, but the BPM/key data isn’t available, so the PRD now treats it as a companion tool with manual song entry. Mid-build, my first GitHub account was suspended, so I recreated the repo on a new account. After that, I rebuilt the prototype from scratch with Claude’s help. The PRD itself didn’t change.
  • Cost & time this week: $0.00 extra (covered by my Claude Pro plan) · ~9 hours

Build 2 · Smallest Local Version & PostHog (Due Nov 16)

  • What shipped: Springboard now makes a real AI call on my laptop: “Suggest songs that fit” asks a model on OpenRouter for real songs outside my crate that match the set’s genre, style, Camelot keys and tempo, through a small local server that keeps my API key out of the browser and out of GitHub. PostHog tracks pageviews, clicks and session replays on this page and the app. I also reorganized the app into four steps (pick a starting song, shape the set, view the set, edit in My crate). My crate now warns when a dragged track creates too big a Camelot or BPM jump. PRD v2 and AGENTS.md are updated.
  • Things learned: API keys belong in a server-side .env file, not in a web page. PostHog’s autocapture records clicks without extra code.
  • What broke / changed in PRD: The prototype changed from picking one next song (DJ Sounding Board) to building a whole set from one starting song (Springboard). The AI button only works when the app runs through server.py; on GitHub Pages it hides itself.
  • Cost & time this week: ~$0.05 in OpenRouter API calls (plus my $20/month Claude Pro plan) · ~5 hours

Build 3 · Build.exe: The Core Workflow (Due Nov 23)

  • What shipped: A full redesign (multiple sets on a home page, a dark DJ-board and vinyl look, a slide-out menu, a view-only “Your set” tab with transition timing, and an “Organize set” tab with a floating Camelot wheel). Songs can be added by pasting a list or uploading a playlist screenshot, and the AI checks each song’s BPM, key and genre against music sites online. The app is live on Render with rate limits, and the security audit is in SECURITY.md. PostHog tracks the funnel: set created → songs added → reordered → AI suggestions → set viewed.
  • Things learned: A public AI route needs a rate limit and a spending cap, or anyone can spend my credit. Static hosting (GitHub Pages) can’t keep a secret key, so the app needs a server host.
  • What broke / changed in PRD: PRD v3 adds hosting, data and security choices. I chose browser storage over a database because sets are personal and there’s no sign-in. The free server sleeps when idle, so the first load is slow.
  • Cost & time this week: $0.05 in OpenRouter calls (see openrouter.ai → Activity) · 6 hours
